# Orchestrator

Main control-plane process for a Underleaf cluster. One Orchestrator runs per cluster (on the manager node) and coordinates Agents to realize the repo-backed app manifest model. See the [root README](../../README.md) for how this fits into the overall architecture.

| Info | Value |
| ---- | ----- |
| Language | Golang |
| Architecture | Hexagonal Domain Driven Design |
| Storage | Sqlite3 |

## Directory Structure

```
cmd/
    cli/      -- orcli binary (operator/user CLI)
    server/   -- orch-server binary (long-running daemon)
    migrate/  -- migrate binary (applies repository/migrations)
interface/
    cli/            -- orcli command implementations
    grpc_public/    -- Agent -> Orchestrator gRPC (:50100)
    cluster/        -- the cluster listener (mTLS) and the join endpoint
link/               -- the agent link: hub of live links, command routing
    grpc_private/   -- internal/orchestrator-to-orchestrator gRPC
    rest/           -- REST API for the Orchestrator UI (http://127.0.0.1:9090/api)
repository/
    migrations/     -- Sqlite schema migrations
service/            -- domain/business logic
types/              -- domain types
utils/              -- shared helpers local to the orchestrator
```

## Interfaces

| Protocol | Purpose | Location |
| -------- | ------- | -------- |
| gRPC | Unix socket management API for CLI | `unix:/tmp/undf-orch.sock` |
| gRPC | Agent-Orchestrator communication, **local listener** (single-node install; unauthenticated, loopback only). Serves `OrchestratorPublic` and the agent link | `127.0.0.1:50100` |
| gRPC (mTLS) + HTTPS join | **Cluster listener**: worker nodes. Exists only after `orcli nodes add`; client certificates from the cluster CA are required | `0.0.0.0:50104` (advertised address is what nodes dial) |
| http | REST API at `/api/v1/` and, from the same listener and origin, the built Orchestrator UI at `/` (served from `UNDERLEAF_UI_DIR`; unset means API only) | `http://127.0.0.1:9090/` |

Routes today: nodes, containers, logs, deployments, `/health` (see `interface/rest/*.go`). There is **no CORS**: the UI is same-origin (served by the Orchestrator, or proxied by the Vite dev server), and cross-origin callers are refused by the Origin guard.

## Security model

The orchestrator has **no per-user authentication** on the local listeners (REST and the local gRPC) or the CLI socket. Anyone who can reach one of them can deploy workloads (which run on an agent's Docker daemon), read container logs, and open metered streams. The trust boundary for those is therefore the local host, and the controls below keep it there. Anything that crosses the network does so on the **cluster listener**, which requires mutual TLS. There are no other switches: no shared token, no "allow remote" flag.

| Control | Behavior |
| ------- | -------- |
| Loopback bind | The unauthenticated TCP listeners (REST `:9090`, local gRPC `:50100`) bind `127.0.0.1`, always. `UNDERLEAF_BIND_ADDR` may name another loopback address, but `utils.ListenLocal` refuses anything else (startup fails with an explanation); no environment variable widens it. Agents have no TCP listeners at all. |
| Cluster CA | On first start the Orchestrator generates a cluster-local CA (ECDSA P-256, 10 years) in `cluster-ca/` beside its database (dir `0700`, key `0600`, never leaves the manager). It is unrelated to the cloud CA. The trust bundle (`trust_bundle.pem`) can hold more than one CA so a rotation stays possible. |
| Cluster listener | Opened by the first `orcli nodes add`, never before. Built by `utils.ListenCluster`, which refuses to construct a listener whose mTLS side does not require and verify client certificates, so a non-loopback listener cannot exist without mTLS. One port, two sides told apart by ALPN during the handshake: **h2** (gRPC) needs a client certificate chaining to the cluster CA; **http/1.1** reaches only the join endpoint (`POST /v1/join`), which authenticates the server only because a joining node has no certificate yet, and can never reach gRPC. Certificates on the deny list are refused at the handshake and again on every RPC, so `nodes rm` also cuts connections that are already open. A member may only report its own containers and cannot create or list nodes. |
| Join | `orcli nodes add` prints one opaque `ulj_…` string: manager address + SHA-256 fingerprint of the cluster CA + a 256-bit single-use secret (15 minutes). The node verifies the manager's certificate chain against that fingerprint **during the TLS handshake, before sending anything**, so the secret is never offered to an impostor. The manager stores only the secret's hash, consumes it on first use, and answers a wrong, reused or expired secret identically. Node certificates: 730 days, `NotBefore` backdated 5 minutes, client-auth only, CN = node id (the CSR's other requests are ignored). Renewal starts 90 days before expiry over the live mTLS connection and is retried daily; a node whose certificate expired re-joins with a fresh string and keeps its id. `orcli nodes ls` shows each expiry and warns at 30 days; `orcli nodes rm` revokes every certificate of the node (deny list keyed by serial, pruned after the certificate would have expired anyway). |
| Agent link | Agents dial out; the Orchestrator never connects to an agent and has no address for one (`shared/clients.AgentDirectory` resolves a *node id* to its live link, nothing else). Commands travel down one gRPC bidirectional stream per node and results come back matched by request id; open-ended output (log follow) gets its own sub-stream, attached with a single-use token bound to the node it was issued for. On the **cluster listener** the node is the CN of the client certificate that passed mTLS; the hello cannot say otherwise, and `nodes rm` / re-enrollment drop the live link. On the **local listener** there is no credential (loopback only, like the rest of the local surface): the agent names its node, the node must be a `local`-transport node (the manager's own agent), and a link may *not* claim a node that joined through the cluster listener. A rogue local link can therefore only receive the local node's commands and answer them falsely or occupy its slot; it cannot make the Orchestrator or an agent do anything, which is the reverse of the old exposure, where any local process could drive the agent's Docker through `:50101`. Deployments are placed on a node by link (sticky per deployment; a down node is a clear error, never a silent move). |
| CLI sockets | `/tmp/undf-orch.sock` and `/tmp/undf-agent.sock` are created `0600`. The CLI refuses to dial a socket not owned by the current user, since requests can carry GitHub tokens. |
| Browser guards (REST + UI) | Apply to every request on the listener, including UI assets and WebSocket upgrades: a loopback `Host` (DNS rebinding); an `Origin`, if one is sent, that is this server's own origin (its authority equals the request's `Host`, so the UI works on any published port) or is allowlisted (CSRF); `Content-Type: application/json` on POST/PUT/PATCH. The log WebSocket uses the same Origin policy. Extend with `UNDERLEAF_ALLOWED_ORIGINS` / `UNDERLEAF_ALLOWED_HOSTS` (comma-separated). Responses carry `X-Frame-Options: DENY` / CSP `frame-ancestors 'none'` / `nosniff`, so another site cannot frame the UI. |
| SQL | The `SqlQuery` RPC and `orcli sql` exist only in `-tags devmode` builds, and run on a read-only connection with `ATTACH` disabled. |
| Install | The Orchestrator is a **native process**, not a container, and there is no Docker image of it. `install.sh` downloads `orch-server`, `orcli`, `ufagent`, `ufagentd` and the built UI, then runs `orch-server` as a launchd user agent (macOS) or systemd user service (Linux) with its state directory as the working directory. `orcli` is a plain command that talks to the Orchestrator's unix socket directly. **State** lives in one directory only you can read (`~/Library/Application Support/Underleaf` on macOS, `$XDG_DATA_HOME/underleaf` or `~/.local/share/underleaf` on Linux; `UNDERLEAF_DATA_DIR` overrides): the database (which holds API tokens), the cluster CA and its private key, cloud-issued certs, the UI files, and the agent's own `agent/` subdirectory. The cluster listener (`50104`) listens on all interfaces once the first `orcli nodes add` opens it, and accepts mutual TLS only; nothing needs publishing. Docker is used by the agent alone, to run workloads. An earlier Docker-based install is migrated automatically by re-running `install.sh`: its state is copied here and the old container is kept, stopped, as a backup. |
| Stream port denylist | A gateway stream publishes a local port to the internet, so it may never target the control plane. [`shared/utils/controlports.go`](../../shared/utils/controlports.go) defines the denied set once: Orchestrator REST/gRPC (`9090`, `50100`), the cluster listener (`50104`, and wherever `UNDERLEAF_ORCH_LOCAL_PORT` / `UNDERLEAF_ORCH_CLUSTER_PORT` move them), the ports older agents listened on (`9091`, `50101`, `50103`; current agents listen on none), the Docker daemon API (`2375`/`2376`), the **configured** REST ports from `UNDERLEAF_CONFIG`, plus anything in `UNDERLEAF_EXTRA_CONTROL_PORTS` (comma-separated; set it if you publish the control plane on other host ports). Invalid ports (`<1`, `>65535`) are refused too. Enforced twice: at stream creation in the Orchestrator (before anything is provisioned in the cloud) and in the agent, both when it accepts the request and where it dials the local port to forward. The agent check is authoritative since only it knows its own configuration. |
| Network isolation | The agent puts every workload on its own user-defined Docker network (`underleaf-workloads`, override `UNDERLEAF_WORKLOAD_NETWORK`; the default bridge and `host` are refused), so workloads cannot reach each other's unpublished ports or anything else on the default bridge. The Orchestrator is a host process bound to loopback. **Limit:** on Docker Desktop (macOS, Windows) a container can reach host loopback services through `host.docker.internal`; checked on macOS: a workload reached both `50100` and `9090` that way (the REST Host-header guard rejects the name, but a forged `Host` header gets through). On Linux Docker Engine a container cannot reach a host service bound to `127.0.0.1`, which is the stronger position; this has not been run here. **This is an accepted limit** (RFD 5, "Local trust and its limits"): the local path stays unauthenticated by decision, so on Docker Desktop do not deploy workloads you do not trust with the host. |
| API tokens | `orcli tokens create --scope read\|deploy\|admin --ttl 30d [--name ...]`, `orcli tokens ls`, `orcli tokens revoke <id>`, minted **only over the owner-only unix socket** (never REST or TCP). A token is a bearer credential (`Authorization: Bearer ulat_<id>_<secret>`); only SHA-256(secret) is stored, the secret is shown once, and every token expires (1 minute to 365 days). Scopes are hierarchical (admin > deploy > read) and enforced per route from one table, `routeScopes` in [`interface/rest/auth.go`](interface/rest/auth.go): `read` = GET-style calls, `deploy` = `POST /deployments`, `admin` = everything else, and **any route not in the table requires admin** (a test fails if a route is unlisted). `deploy` runs Docker on the host and is root-equivalent. A malformed, unknown, expired or revoked token is a `401`, never a fall-through to the local path. |
| Local path vs. tokens | A request with **no** `Authorization` header is the local operator/UI and has full access (RFD 5, "Local trust"), so on a default install a token narrows nothing for a caller who simply omits it: tokens are for automation (revocable, expiring, scoped) and are what the remote listener will enforce. Set `UNDERLEAF_REQUIRE_TOKEN=1` to make every API route except `/health` require a token (the UI then needs a token and will not work without one; UI token entry is not built). |
| WebSocket tickets | Browsers cannot set headers on a WebSocket, so the UI calls `POST /api/v1/ws-tickets` (read scope) and opens the stream with `?ticket=`. A ticket is 256 random bits, valid 30 s, **single use** (consumed on first use), carries the scope of whoever minted it, works only on WebSocket routes, and is scrubbed from access logs. At most 1024 are outstanding. Revoking a token does not cancel tickets it already minted (they die within 30 s). |

| Remote listener (off by default) | Remote access (Cockpit, `ufctl connect`) is a **second** HTTP listener, enabled only by `UNDERLEAF_REMOTE_ADDR=host:port` (bind policy as for the REST listener; publish it on loopback only). It serves the same UI and API on one origin, but **every** request, static files and `/health` included, needs a valid cloud-signed assertion in the `X-Underleaf-Assertion` header; there is no unauthenticated or local-principal path. The assertion's scope (highest of `read`/`deploy`/`admin`) is checked against the **same** `routeScopes` table as API tokens; unlisted routes need admin. `Authorization` headers, API tokens, WebSocket tickets and forwarded-identity headers (`X-Subject-Id`, `X-Forwarded-*`) are not credentials there. Host and Origin guards do not apply (the browser's are the cloud's; the cloud authenticated the request before signing); JSON-only bodies still do. |
| Assertions | Ed25519 JWS (`EdDSA`, `typ` `underleaf-assertion+jwt`, `kid`), ≈60 s, claims `iss`/`sub`/`aud`/`scopes`/`iat`/`exp`/`jti`, verified by [`shared/assertion`](../../shared/assertion). Rejected: wrong or missing audience (this cluster's id is the CN of the cloud-issued cluster certificate; unregistered means everything is rejected), expired or over-long lifetime, no recognised scope, unknown `kid`, bad signature, any other algorithm (`none`, HMAC, RS256), and a `jti` already seen (in-memory cache until `exp` + leeway; a restart forgets it, leaving a replay window of at most one assertion lifetime). |
| Assertion keys | The cloud's public key set (`GET {cloud}/assertion-keys`) is fetched at start and then hourly (every minute while failing, e.g. before registration), **persisted** to `<cert_dir>/assertion_keys.json` and verified from that copy, so a cloud outage or restart does not break verification. No key ever fetched means every assertion is rejected. Keys are kept until their stated `not_after`; a fetched set replaces the cache (a key the cloud withdrew is dropped at once), but an empty or invalid answer keeps the previous set. An unknown `kid` triggers at most **one refetch per minute** (failed attempts count). The fetch uses TLS pinned to the CA chain from registration (`ca_chain.pem`, never system roots) and verifies the host name against the server certificate. Point it at the cloud's dedicated **pinned listener** with `assertion_keys_base_url: https://<cloud host>:8443/api/v2/cloud` in the config file (default: `cloud_api_base_url`). That listener always presents the CA-issued server certificate, so it keeps working if the main port later serves a public certificate. A certificate with no names (an older cloud that still presents the CA certificate itself) is accepted on chain alone, a weaker check kept only so an old cloud keeps working. Plain `http` is accepted for loopback hosts only. |
| Local listener vs. assertions | The loopback listener never reads an assertion and answers `403` to any request that carries `X-Underleaf-Assertion` or `X-Subject-Id`, so tunnelled traffic misdirected to it fails closed instead of inheriting the unauthenticated local principal. |
| Tunnel path | The cloud opens a stream **toward** the agent on the agent's existing outbound connection and writes `UNDERLEAF-REMOTE/1\n`; the agent splices only such streams to the one configured address (`UNDERLEAF_REMOTE_TARGET`), never to a destination the stream names, and refuses all cloud-opened streams when it is unset. Gateway streams run the other way (agent-opened, bound to a port the agent chose), and the remote listener's ports (`50110`, `UNDERLEAF_REMOTE_ADDR`, `UNDERLEAF_REMOTE_TARGET`) are on the stream denylist. The agent keeps a connection open for this with `UNDERLEAF_REMOTE_CONNECTION_ID`. |
| `ufctl login` / `connect` | `ufctl login` runs a device flow and stores a revocable device key at `<user config dir>/underleaf/ufctl/device.json` (dir `0700`, file `0600`, refused if loose). `ufctl connect <cluster>` serves `http://localhost:<port>` on **127.0.0.1 only** and forwards to `{cloud}/clusters/<id>/remote/...` with the device key; it checks Host (DNS rebinding), Origin and `Sec-Fetch-Site` (cross-site pages), rejects dot-dot and encoded-slash paths, and strips browser-supplied credentials. The device key is sent only to the cloud URL it was issued for, over https (or loopback http). **Cloud side not built yet:** see the RFD 5 journal, step 7b. |

Not covered yet: UI login or token entry for strict mode, and per-service container hardening (see `edge/agent/service/docker_service.go`).

## Running locally

From `edge/`:

```bash
make build-dev   # builds orcli, orch-server, migrate, ufagent, ufagentd into edge/bin
make run         # starts orch-server, ufagentd, and the Orchestrator UI via overmind
```

See [edge/Procfile](../Procfile) and [edge/Makefile](../Makefile) for the exact process definitions and build targets, and the [root README](../../README.md#development) for the full local dev workflow.
